# 2017年製 Intel iMac へのローカルLLM推論環境構築 — CPUのみで実用速度を出すためのモデル選定と組み込み

## 概要
Apple Silicon を搭載しない 2017年製の Intel iMac（GPU 加速なし・CPU 推論のみ）に、ローカルで動作する LLM（大規模言語モデル）の推論環境を構築した。量子化済みの小型モデル3種を同一条件でベンチマークし、応答速度・メモリ使用量・出力精度の実測値をもとに採用モデルを決定。決定したモデルを、ローカル HTTP API 経由で既存の Python アプリケーションへ組み込み、推論サーバが停止していてもアプリが動作し続ける構成にした。

## 使用技術（言語・ツール）
- **Ollama 0.31.1**：ローカルLLMの実行ランタイム。`localhost:11434` に HTTP API を提供する。公式配布のユニバーサルバイナリ版を使用
- **Llama 3.2 3B / Qwen2.5 3B / Gemma 2 2B**：比較対象のモデル。いずれも4bit量子化（Q4）版で、ディスク占有は各 1.6〜2.0GB
- **Python 3.9.6**：クライアントおよびベンチマークの実装言語（macOS 同梱バージョン）
- **requests 2.32.5**：推論APIの呼び出しに使用
- **pytest**：クライアントの単体テスト。推論サーバに接続せず、異常系を含めて検証できるようHTTP層をモック化
- **実行環境**：macOS 13.7（Ventura）／Intel Core i5-7500（4コア4スレッド・2017年）／メモリ 16GB

## 構築したもの
1. **CPU推論環境** — Intel Mac 上に Ollama を導入し、量子化モデル3種を取得して切り替え可能にした構成
2. **モデル比較ベンチマーク** — 同一プロンプト・同一パラメータ（`temperature=0`・`num_predict=80`）で3モデルを走らせ、1件ごとの応答秒数と出力の正誤を計測するスクリプト。課題は「日本語の短い単語を、英語の説明句と4値の分類ラベルからなる JSON に変換させる」構造化出力タスク10件（正解が既知の6件＋正解を用意していない4件）を few-shot で与える形にした
3. **アプリ組み込みクライアント** — 推論APIを呼ぶ薄いモジュール。タイムアウト設定、コードフェンス混じりの応答からの JSON 抽出、値のホワイトリスト検証、例外を呼び出し元へ漏らさない失敗時フォールバックを実装
4. **単体テスト** — 正常系・コードフェンス付き応答・不正な分類値・空文字・パース不能・接続不可・空入力の7ケース
5. **運用ルール** — 常駐させず必要時のみ起動する手順と、メモリ逼迫時にモデルを降ろす手順を文書化（同一マシンで別の重い処理を動かすため）

## 解決した技術的課題

| # | 症状 | 原因 | 対処 |
|---|---|---|---|
| 1 | パッケージマネージャ経由で導入したランタイムが、**終了コード0で完了したのに起動しない** | Homebrew 6 では Intel + macOS 13 の組み合わせがビルド対象外（Tier外）となっており、ソースビルドが失敗しているのにコマンド自体は成功として終了していた | 公式配布のユニバーサルバイナリ版へ切り替えて解消。以後、導入結果を終了コードで判断せず、実際に起動・応答させて確認する手順に変更 |
| 2 | 7B以上のモデルは数トークン/秒しか出ず実用にならない | Apple Silicon・dGPU をいずれも搭載せず、CPU 推論のみで動作するため | 2〜3B クラスの4bit量子化モデルに候補を限定。加えて `num_predict=80` で出力長を、`temperature=0` で揺れを抑え、用途を短い構造化出力に絞る設計とした |
| 3 | モデルが JSON 以外（コードフェンス・前置きの説明文）を混ぜて返し、パースに失敗する | 小型モデルは出力形式の指示追従が大型モデルより不安定 | コードフェンスを除去 → 最初の `{` から最後の `}` までを切り出してパース → 分類ラベルを許容値の集合と照合、という3段の防御を実装。いずれかで外れたら失敗として扱う |
| 4 | 初回リクエストだけ数十秒かかり、タイムアウトする | モデルのメモリロードが初回リクエスト時に発生する仕様 | タイムアウトを60秒に設定。2回目以降は数秒で応答することを実測で確認し、初回のみ遅延する前提を運用手順に明記 |
| 5 | 推論サーバを停止した状態でアプリ全体が停止する | 接続エラーがアプリ層まで伝播していた | 接続不可・タイムアウト・パース不能・値不正をすべて同一の失敗値に畳み、該当の入力だけ除外して処理を継続する設計（graceful degradation）に変更。推論サーバが落ちている状態の挙動を単体テストで固定した |
| 6 | 採用したモデルの利用条件が後から問題になるリスク | 小型モデルは配布元ごとに利用条件が異なり、用途が制限されるものもある | `ollama show <model> --license` で条文の原文を確認したうえで採用を決定。組み込み時に求められる帰属表示も併せて実装した |

## リポジトリの構成
- `benchmark.py` — モデル比較ベンチマーク（応答秒数・分類正答数を出力）
- `ollama_client.py` — アプリ組み込み用クライアント（タイムアウト／JSON抽出／値検証／失敗時フォールバック）
- `test_ollama_client.py` — 上記の単体テスト7件

いずれも実際に使用したコードを、汎用的な課題設定に置き換えて公開用に整理したもの。下表の計測値は元のコードで得た実測値であり、課題設定が異なるため `benchmark.py` の実行結果とは一致しない。

```bash
ollama serve                      # 別ターミナルで起動
python3 benchmark.py llama3.2:3b  # 応答秒数と正答数を計測
python3 -m pytest                 # 単体テストは推論サーバ不要
```

## 結果
- **2017年製の CPU のみの機材でローカルLLM推論が成立**した。応答は平均2.8秒（最遅9.5秒）で、目標としていた「10秒以内」を全件でクリア
- **推論時のメモリ使用量は約2.2GB**。16GB のマシンでブラウザや他の作業と同居できることを実測で確認
- **3モデルのベンチマークで採用モデルを決定**した（下表）。応答速度は上位2モデルが同等だったため、出力精度と利用条件で判断。日本語性能の高いモデルが1つあったが、利用条件を原文で確認できなかったため候補から外した

  | モデル | 平均応答 | 正解が既知の6件の分類正答 | 正解未設定4件の妥当性（目視） |
  |---|---|---|---|
  | Llama 3.2 3B | 2.8秒 | **6/6** | 3/4 |
  | Qwen2.5 3B | 2.8秒 | 4/6 | 4/4 |
  | Gemma 2 2B | 5.1秒 | 3/6 | 1/4 |

- **既存 Python アプリへの組み込みまで完了**。推論サーバの停止時も機能を縮退させて動作し続けることを単体テスト7件で保証
- 追加のハードウェア費用・API 従量課金をかけずに、ローカル完結の推論環境を用意できた
